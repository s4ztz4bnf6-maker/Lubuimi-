# JARVIS runtime audit — 2026-11-19

## Worker source recovery

The autonomous worker was not an opaque binary-only service. Its Railway start command contained a compressed/encoded Bun program. The source was decoded from the production service configuration and recovered at 115499 characters.

The public mirror deliberately redacts the two hard-coded Bitcoin receive addresses. The resulting `ownerReceiveAddresses` list is empty in this public snapshot; this is a privacy scrub, not a deployable configuration. Do not deploy this scrubbed mirror. The production runtime remains the source of truth.

## Parallel execution

The worker reads `JARVIS_MAX_PARALLEL_TASKS` and clamps it to the inclusive range 1–4. It claims up to that number of tasks in a DB transaction using `FOR UPDATE SKIP LOCKED`, then processes the batch with `Promise.all`. The same cap is applied to both free-task and standard-task queues.

Current production config: one replica in `iad`, cron `1-56/5 * * * *` (approximately every five minutes). The worker is not continuously running. 24-hour metrics sampled 1,441 points: current CPU 0, average CPU ~0.00048, peak CPU ~0.01583; current memory ~0.0406 GB, average ~0.0343 GB, peak ~0.1145 GB.

A two-task cap is staged as a pending Railway variable change. It is not live until the owner commits the staged Railway deployment. No replica increase was made: multiple cron replicas could execute the same scheduled cycle unless the scheduler is explicitly made singleton-safe.

## Companion UI

The development mirror changes the base font from 15px to 16px. This is a mirror-only change; the production Companion service has not been modified or redeployed.

## Security findings

- Worker source had two literal Bitcoin receive addresses. They were removed from this public mirror.
- No literal API-key/secret/password assignments were detected by the simple source scan. This is not a complete secret audit.
- Environment variable names were inspected, but values were withheld by the connected Railway authorization.

## Next engineering gates

1. Add unit tests for task-claim concurrency, queue fairness and retries.
2. Add an explicit singleton/lease mechanism before scaling cron replicas.
3. Separate runtime secrets and receive addresses from source code.
4. Run staging integration tests before any production deploy.

## Public repository privacy note

The repository is public. Earlier commits on this mirror branch briefly contained literal Bitcoin receive addresses copied from the live Companion source before the privacy scan found them. The current source file replaces those literals with `REDACTED_BTC_RECEIVE_ADDRESS`, but Git history may retain the earlier values. Treat those receive addresses as publicly linkable; they are not private keys and do not permit spending, but they can affect transaction privacy. The owner should use fresh receive addresses for future receipts if they want to unlink activity. No seed phrase or private key was found or exported.
